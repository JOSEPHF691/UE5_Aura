# 游戏客户端秋招深度面试题与参考答案

本手册用于 Aura 项目的游戏客户端开发岗模拟面试。难度按头部游戏公司高标准校招面试设计，重点考察 C++、Unreal Engine、Gameplay Ability System、实时联机、AI、性能、图形学、操作系统、网络和现场设计能力。

参考答案以“合格到优秀的秋招回答”为尺度：先给结论，再讲机制，最后用 Aura 中的真实代码或测试作证，并主动说明边界。不要逐字背诵。能画出数据流、指出失败路径并根据追问修改代码，才算真正掌握。

## 使用方法与评分标准

推荐分三轮练习：一面 60 分钟考 C++、UE 和算法；二面 75 分钟深挖 Aura 项目、GAS、AI 与联机；三面 60 分钟考性能、系统设计、故障定位和项目复盘。

每题按 0–4 分评分：

- 0 分：概念错误，或把未实现功能说成已实现。
- 1 分：只会给结论和名词，解释不了调用链。
- 2 分：能说清机制和主要数据流，达到基本秋招要求。
- 3 分：能结合 Aura 的类、状态和验证方式，并说明边界条件。
- 4 分：能讨论替代方案、性能或并发风险，并能现场落到代码修改。

回答项目题时使用四段式结构：“需求是什么 → 数据归谁所有 → 调用链如何运行 → 如何验证及还有什么限制”。

## 第一部分 项目总览与架构

### 1. 请在 90 秒内介绍 Aura，不能按功能清单念简历

**秋招参考答案：**

Aura 是我用 UE5.7 和 C++ 完成的上帝视角动作 RPG 地牢纵切。我重点解决的不是单个技能，而是让战斗、AI、关卡状态、个人战利品、成长经济和双人联机形成同一套服务器权威闭环。玩家技能基于 GAS：Q 是地面选点，E 是方向施法，普攻支持点击锁定、二级追踪和三级互斥分支；三种技能还能通过服务器记录的标记与 Cast ID 形成 Combo。敌人使用 AIPerception、导航和 C++ 状态机，包含近战、远程后撤、精英专属技、韧性条和两阶段 Boss。

工程上，背包和装备放在 PlayerState，使用 Fast Array 增量复制并限制为 Owner Only；房间、封印和 Boss 入口放在 GameState 或关卡 Actor；交易由可靠 RPC 发起，服务器校验距离、状态、资源和物品 GUID。单机存档使用 v5 schema，先校验旧结构，再迁移到内存，非法档会阻止覆盖。项目还配有跨进程存档、双客户端、100/200 毫秒延迟与 1%/3% 丢包等烟测。当前边界是局域网双人合作，没有互联网平台会话和完整断线重连。

**面试官继续追问：** 如果只允许保留两个最有技术含量的点，我会保留“预测技能的目标数据与服务器结算”和“Fast Array 私有背包 + GUID 事务校验”，因为它们最能体现客户端岗位需要的实时交互、状态一致性和调试能力。

### 2. 这个项目的核心架构如何分层

**秋招参考答案：**

我按“表现、规则、持久状态、世界状态”分层。PlayerController 处理本地输入、鼠标命中、UI 模式和请求发起；Character/Enemy 承载可见角色、移动、动画和 ASC；GameplayAbility 负责一次施法流程，GameplayEffect 修改属性和状态；PlayerState 保存死亡后仍应存在的个人成长、背包和装备；GameState 保存全队共享的封印、检查点和清房状态；EncounterVolume、Gate、Chest 等关卡 Actor 负责房间状态机；GameInstanceSubsystem 负责跨地图的单机运行快照和 SaveGame。

判断状态放在哪里的原则是生命周期和可见范围：只影响本机操作的放 Controller；随 Pawn 重生的放 Character；跨 Pawn 但属于个人的放 PlayerState；所有客户端共享的世界进度放 GameState；跨地图且只服务单机磁盘持久化的放 GameInstanceSubsystem。

### 3. 为什么背包放在 PlayerState，而 ASC 却放在 Character

**秋招参考答案：**

背包和装备必须在角色死亡、Pawn 销毁和重新占有后仍存在，所以放在 PlayerState 很自然。当前 ASC 是 Character 的子对象，优点是 Avatar 和 Owner 简单、敌人与玩家共用 CharacterBase、施法动画和属性访问直接；缺点是 Pawn 重建时要重新初始化 ActorInfo、重新授予能力、从 PlayerState 同步成长和装备效果，临时 GameplayEffect 也不会天然跨 Pawn 保留。

如果项目要做更完整的掉线重连、换角色或跨 Pawn 持续 Buff，我会考虑把玩家 ASC 放到 PlayerState，OwnerActor 是 PlayerState、AvatarActor 是当前 Pawn，并在 PossessedBy、OnRep_PlayerState 和重生时重新 InitAbilityActorInfo。当前方案对小型纵切足够，但我要能明确说出这个取舍，而不是声称 ASC 已经天然跨死亡持久化。

### 4. 为什么使用 GAS，而不是在 Character 中手写技能冷却和伤害

**秋招参考答案：**

GAS 把能力授予、激活条件、消耗、冷却、属性修改、标签状态和网络预测放进统一协议。Aura 中 FireBolt、Q、E 都通过 Ability 激活，法力和冷却通过 GameplayEffect 提交，伤害通过 SetByCaller 写入 EffectSpec，眩晕、减速和死亡等状态通过标签协作。这避免每个技能各写一套计时器和网络分支，也便于装备效果、Combo 和技能等级叠加。

代价是学习成本和状态时序更复杂，例如预测实例不能过早结束、目标数据必须按 PredictionKey 对齐、表现与权威伤害要分开。小型纯单机技能少时手写更快；一旦有联机、Buff、装备和多技能组合，GAS 的统一性更有价值。

### 5. Aura 中一次“左键火球命中敌人”的完整调用链是什么

**秋招参考答案：**

鼠标按下时 PlayerController 先缓存光标下的敌人，再由 Enhanced Input 的 PrimaryAttack 调用 ASC 的 TryActivateAbilityByClass。FireBolt 是 LocalPredicted：本地构造 Actor TargetData，并通过 PredictionKey 发送给服务器；两端进入 HandleTargetData，服务器重新校验目标存活、距离和墙体遮挡。CommitAbility 成功后扣除配置的消耗并添加冷却，角色按目标方向转身；释放时只有服务器生成复制投射物。

投射物在服务器碰撞，构造 Damage GameplayEffectSpec，写入 Data.Damage 和 Data.PoiseDamage，再应用到目标 ASC。AttributeSet 先做护甲减伤和 Boss 护盾吸收，随后更新生命、韧性和死亡奖励。命中后服务器还根据 Cast ID 消耗或添加 Combo 标记。客户端看到的是预测施法表现、复制的投射物和服务器广播/复制的命中结果。

### 6. 项目里哪些状态是“个人状态”，哪些是“共享状态”

**秋招参考答案：**

个人状态包括背包完整条目、装备实例、魂、技能点、技能等级、火球分支、个人宝箱领取和个人 Combo 标记；这些主要在 PlayerState、InventoryComponent、EquipmentComponent 或拥有者 Character 上，并尽量 Owner Only。共享状态包括房间是否清理、门是否开启、已激活封印、Boss 是否召唤、检查点和本局是否通关，放在 GameState 或复制的关卡 Actor。

这样划分既减少带宽，也避免语义错误。例如封印若做成普通背包物品，玩家丢弃或掉线可能让队伍软锁；所以它是 GameState 的队伍任务状态。装备详情不需要广播给所有人，其他玩家只需看到角色外观摘要。

### 7. 数据驱动在 Aura 里具体体现在哪里

**秋招参考答案：**

战斗数值集中在 AuraCombatBalanceData，包含玩家属性、技能伤害和消耗、AI 感知、敌人、精英、Boss、韧性、成长和经济；掉落预算在 LootProfileData；物品静态信息在 ItemDefinition，运行时实例只保存品质、等级、随机词条、强化值和来源。C++ 负责不变量和流程，Data Asset 负责可调参数。

数据驱动不等于所有规则都放表里。比如“火球是免费兜底攻击”“Q/E 单次伤害高于火球”“Boss 弹幕冷却必须覆盖完整施法周期”属于校验不变量，代码会拒绝非法配置。这样策划能调数值，但不能把系统调进明显错误状态。

### 8. 你如何保证一次交易不会只扣钱不发物品

**秋招参考答案：**

交易入口只接受客户端意图，实际操作在服务器。服务器先验证 NPC、距离、角色状态、商品、资源和背包容量，再执行状态变更。对打造等操作，应该先构造候选结果并检查可接收，再扣材料和魂，最后提交物品；任何检查失败都应零副作用。Aura 的商店、打造和熔炼还携带 RequestId，重复请求会被拒绝，避免重发导致重复扣款。

我会特别说明当前去重集合最多保存 256 个 GUID 且没有淘汰或结果缓存，适合短 Demo，但不是生产级事务系统。正式方案会使用每玩家递增序列号或带 TTL 的 LRU，并缓存已完成请求的结果，使网络重试得到相同响应而不是静默丢弃。

### 9. 你认为项目中最值得现场讲解的一次问题定位是什么

**秋招参考答案：**

可以讲“左键偶发不释放技能”。现象看似是 GAS 激活失败，实际是输入和视口捕获时序问题：点击后 SceneViewport 可能改变捕获状态或光标位置，Enhanced Input 回调再次查询鼠标时，命中结果已经变化或取不到。修复不是增加重试，而是在原始 MouseDown 的 InputKey 阶段缓存目标弱引用和 0.2 秒有效期；Ability 激活时消费快照，服务器仍重新校验目标。Q/E 确认同样消费上一帧已经显示给玩家的预览，而不是在捕获后的同一点击里重新采样。

这个案例能说明我会沿输入事件、视口捕获、Ability 激活和服务器目标数据逐层打日志，区分“请求没发出、Ability 被拒绝、目标丢失、伤害未结算”四类故障。

## 第二部分 GAS、输入与战斗底层

### 10. LocalPredicted、ServerOnly 和 ServerInitiated 有什么区别，Aura 如何选择

**秋招参考答案：**

LocalPredicted 允许拥有者客户端先执行可预测部分，同时把激活和目标数据发给服务器，服务器确认或拒绝；适合玩家主动技能，能降低按键到表现的延迟。ServerOnly 只在服务器运行，客户端不能本地启动权威逻辑；Aura 的敌人近战、萨满和 Boss 技能使用它。ServerInitiated 是服务器发起，但客户端也会建立对应能力实例，适合由服务端事件驱动又需要两端 Ability 流程的场景。

选择标准不是“玩家就预测、敌人就不预测”这么简单，还要看结果是否可回滚。伤害、生成投射物和掉落必须权威；动画、瞄准框和声音可以预测或多播。

### 11. PredictionKey 在 GAS 中解决什么问题

**秋招参考答案：**

客户端预测会先产生一次本地激活、消耗或标签变化，服务器稍后也会执行对应操作。PredictionKey 用来把两端的这一次操作关联起来，使服务器确认时不会把预测结果再叠一遍，拒绝时可以回滚预测状态。目标数据委托也按 AbilitySpecHandle 和 ActivationPredictionKey 匹配，避免不同施法的数据串线。

Aura 的 Q/E/火球在本地构造 TargetData，并在 FScopedPredictionWindow 中调用 CallServerSetReplicatedTargetData；服务器注册对应委托，消费目标数据后再提交能力。现场如果出现双扣蓝或重复冷却，我会先检查是否绕开了 CommitAbility 或 PredictionKey。

### 12. CommitAbility 为什么必须在目标验证后调用

**秋招参考答案：**

CommitAbility 会提交成本和冷却。如果目标数据无效、方向为零或地面位置非法时先 Commit，再取消能力，就可能出现“技能没放出来但扣蓝进 CD”。Aura 在解析并校验目标、锁定方向或位置之后才 Commit；Commit 失败则立即 EndAbility。

但客户端输入前的蓝量和冷却检查只用于 UI 反馈，不能替代服务器 Commit。客户端看到可用并不代表服务器状态仍可用，最终以服务器 ASC 为准。

### 13. 为什么左键目标要在 MouseDown 缓存，而不是 Ability 中实时查询

**秋招参考答案：**

因为原始点击、Enhanced Input 回调和视口鼠标捕获不一定发生在同一稳定坐标语境。GameAndUI 模式、CaptureDuringMouseDown 或焦点切换都可能让后续 GetMousePosition 失败或坐标跳变。Aura 在 InputKey 收到 LeftMouseButton Pressed 时获取目标，保存 TWeakObjectPtr、存在标记和 0.2 秒过期时间；Ability 只消费这次输入的快照。

缓存只解决客户端意图稳定性，不能成为信任边界。服务器还要校验目标是否仍有效、是否死亡、距离是否小于 1500、WorldStatic 是否遮挡。

### 14. “点到怪物才锁定，点周围只向前发射”如何实现半个身位容错

**秋招参考答案：**

先使用光标射线的直接 HitActor；若直接命中敌人就尝试锁定。若命中地面，则只接受法线 Z 足够大的同层地面，再遍历候选敌人，计算“鼠标地面点到敌人中心的二维距离减敌人胶囊半径”，这个间隙不超过玩家胶囊半径，也就是约半个身位时才算容错命中。还要检查敌人底部高度与地面点接近，避免跨楼层吸附。

若没有候选，就把 TargetData 留空，施法方向锁定为按下时角色前方。这样不会因为点在敌人附近很远的位置就自动索敌。

### 15. 角色背对敌人点击时，如何先转身再发射而不让输入显得迟钝

**秋招参考答案：**

锁定成功后计算当前 Yaw 与目标方向的角差，用固定角速度插值旋转，并根据角差估算所需时间。释放延迟取技能原始前摇和“转身时间 + 小安全余量”的最大值；释放前再次校验目标并做最终对齐。转身期间暂时关闭 OrientRotationToMovement，结束或 Ability 被取消时恢复原值。

表现上本地立即播放施法起手，权威投射物仍由服务器生成。还要处理目标死亡、越界、角色死亡和 Ability Cancel，确保 EndAbility 总能恢复移动朝向状态。

### 16. 火球一级、二级和三级分支的逻辑是什么

**秋招参考答案：**

一级只有“点击命中时朝目标方向发射，飞出后不追踪”；点空则朝角色前方。二级在有合法锁定目标时给投射物设置 HomingTargetComponent，目标失效后取消追踪并按当前速度继续。三级必须二选一：Pierce 给单发增加有限穿透次数；TripleVolley 则每第五次成功释放用三颗环绕短暂停留、按 0.18 秒间隔依次射出的火球替代普通一发。

三火球每颗是普通伤害的 60%，总伤害 180%；三颗共享一个 Combo Cast ID，避免一次强化攻击重复叠三层标记或触发三次终结。计数由服务器 PlayerState 管理，洗点或切换分支重置。

### 17. Q 的“进入选点模式，再左键释放”如何把预览与实际落点对齐

**秋招参考答案：**

进入模式后每帧用光标射线得到地面点，按施法距离在二维平面裁剪，并再次向 WorldStatic 做垂直地面射线，HUD 使用这个结果画预览。左键确认时直接提交最后一个有效预览到 CommittedTarget，而不是重新查询鼠标。Ability 将该位置封装为 SingleTargetHit TargetData 发给服务器；服务器再次限制距离并投射到真实地面，最终 LockedImpactLocation 同时用于范围伤害和 Niagara。

这套流程避免视觉圈、客户端请求和服务器落点分别走三套坐标算法。生产级还应校验 NavMesh/可施法表面标签和墙后落点规则。

### 18. E 技能粒子方向曾经一直偏，根因一般有哪些

**秋招参考答案：**

常见原因有：预览用角色中心，实际射线从法杖尖端；一个使用鼠标世界点，另一个使用归一化方向；Niagara 参数一端要求 Local Space、另一端要求 World Space；组件本身有旋转或缩放导致二次变换。Aura 最终让预览、碰撞 Sweep 和特效都使用同一个 LockedCastDirection，实际 BeamStart 从武器局部 Bounds 的尖端变换到世界坐标，BeamEnd 等于 BeamStart 加方向乘范围。

当前电束资产的 Beam Start 以局部空间消费，而 Beam End 直接按世界空间消费，所以 Start 先用组件逆变换，End 保持世界坐标。调试时记录组件位置、LocalStart、WorldEnd 和方向点积，点积接近 1 才说明视觉与判定一致。

### 19. 为什么服务器不能直接相信客户端发来的 Q 落点和火球目标

**秋招参考答案：**

客户端可被修改，也可能因为延迟持有过期状态。服务器至少要验证：施法者存活且拥有技能、成本和冷却可提交、目标 Actor 类型和生命周期合法、目标在最大距离内、没有不可穿透遮挡、地面坐标有限且在允许范围。对火球，服务器调用 CanLockTarget；对 Q/E，服务器重新裁剪范围和方向。

客户端 TargetData 代表“意图”，不是“事实”。伤害、物体生成、命中和奖励只能在服务器发生。

### 20. Aura 的伤害结算顺序是什么，为什么顺序重要

**秋招参考答案：**

伤害以负的 Health Modifier 进入 AttributeSet。PreGameplayEffectExecute 先检查无敌或阶段保护，再读取 Damage.BypassArmor；普通伤害按 `RawDamage × 100 / (100 + Armor)` 减伤。若 Boss 有护盾，再由护盾吸收减伤后的伤害，只有溢出部分进入生命。PostGameplayEffectExecute 负责 Clamp、韧性伤害和死亡奖励。

顺序决定数值含义：当前护盾吸收的是已经过护甲的伤害。如果设计希望护盾不吃护甲，应在护甲前吸收，或把护盾做独立 Attribute/ExecutionCalculation。回答时要说清当前代码，而不是只说“有护甲和护盾”。

### 21. 为什么伤害公式采用 `100 / (100 + Armor)`，有什么性质

**秋招参考答案：**

它保证 Armor 非负时伤害始终大于零，且减伤收益递减：100 护甲承受 50%，200 护甲承受约 33.3%。相比线性 `1 - Armor%`，不会轻易达到完全免伤，也更适合装备长期叠加。代码还把护甲夹在 0 到 1000，防止异常数据。

缺点是参数 100 决定曲线拐点，必须结合实际装备区间调；如果有穿甲，需要明确是先减固定值、乘百分比，还是改变公式分母。

### 22. Aura 的三条 Combo 是什么，如何防止一次技能重复触发

**秋招参考答案：**

第一条是火球命中添加 Ember，随后 Q 命中同目标时消耗并触发范围爆炸；第二条是 Q 添加 Fracture，随后 E 消耗并向附近目标连锁，二级还能对普通怪短硬直、对 Boss 施加有冷却的削弱；第三条是 E 添加 Overload，随后火球消耗并触发范围爆炸、打断普通怪预警，二级给玩家短时移速和回蓝强化。

每次权威施法分配 Cast ID。标记记录已经应用过的 Cast ID，同一发穿透或三火球共享 ID，不会重复堆叠；终结侧维护已经消费的 Finisher Cast ID，防止一个范围技能重复消耗。标记还绑定 SourcePlayerState，联机时玩家 A 不能误消费玩家 B 的个人连携。

### 23. 受击动画、眩晕和韧性条如何避免互相抢状态

**秋招参考答案：**

普通命中只扣韧性，并对受击动画设置最小间隔和极短视觉窗口，不再每发火球都锁住 AI。韧性降到零时，服务器施加一次带 Duration 的 Stun Effect，设置 bPoiseBroken 和破防后免疫时间；硬直结束后恢复满韧性，延迟一段时间再自动回复。普通、精英、萨满和 Boss 使用不同最大韧性与硬直时长。

顺序上先结算伤害，再施加眩晕，使 Stun 动画拥有最终状态，不被 HitReact 覆盖。Boss 转阶段时明确移除眩晕并拒绝新控制，避免阶段动画被打断。

## 第三部分 AI、关卡状态机与 Boss

### 24. 为什么 Aura 使用 C++ 状态机，而不是 Behavior Tree 或 StateTree

**秋招参考答案：**

当前 AI 状态只有 Idle、Chasing、Attacking、Retreating、Returning、Stunned 和 Dead，转移条件与 GAS ActionLock、感知距离和导航请求紧密耦合。用 C++ 有限状态机能直接调试每次转移，减少小型纵切的资产维护成本。AIController 每 0.1 秒决策，MoveTo 请求还以 0.22 秒节流。

缺点是扩展到大量行为、并行条件和设计师频繁配置时会形成大分支。若继续做项目，我会把“选目标、移动到战位、选择攻击、脱战回巢”拆成 StateTree Task/Evaluator 或 Behavior Tree Service，C++ 只保留感知、战斗能力和可复用查询。当前简历应写“C++ 状态机”，不能写成 Aura 已用 StateTree。

### 25. AIPerception 在项目里做了什么，为什么还要主动扫描玩家

**秋招参考答案：**

SightConfig 配置发现半径、丢失半径、180 度视野和刺激最大年龄；OnTargetPerceptionUpdated 在看到合法活玩家且有视线时设置目标。主动 AcquirePlayerTarget 是兜底：AI 刚生成、感知事件错过、目标死亡后重新选择或测试中瞬移时，控制器仍能从当前玩家中选择距离最近且有视线的目标。

当前主动扫描用 TActorIterator，对双人和少量怪物可接受，但怪物多时是 O(敌人数 × 玩家数) 且每 0.1 秒重复。我会改为从 GameState 的 PlayerArray 获取候选，或由感知系统维护可见目标集合，而不是遍历世界。

### 26. 怪物在追击边界来回踱步的根因和修复是什么

**秋招参考答案：**

旧逻辑把出生点到怪物的硬 Leash 当作追击边界。玩家站在边界附近时，AI 一帧追玩家，下一帧因超出 Home 半径回巢，进入阈值后又重新感知，形成抖动。修复后，已有目标时按“怪物到玩家的距离是否仍在近似上帝视角范围”决定继续追击，不再因为离巢穴远就立刻掉头；玩家真正离开该范围后清目标并回到 HomeLocation，回巢后再次通过视线感知。

进一步可以加滞回：AcquireRadius 小于 LoseRadius，并让 Returning 状态在回到一定范围前不重新锁定，避免阈值噪声。

### 27. 萨满后撤为什么不能简单沿反方向 MoveTo

**秋招参考答案：**

反方向点可能在墙外、悬崖下或投影到玩家身后。Aura 先计算远离玩家的方向，再尝试 0、±42、±78 度多个候选点，用 NavigationSystem 投射到 NavMesh，要求新点与玩家的距离至少增加 35，再选择分离距离最大的点。距离合适且有清晰射线时停止移动并施法；太近则后撤；太远或被墙挡则接近到理想距离。

更成熟的方案会加入 EQS，对可达性、视线、队友占位、危险区域和与玩家距离加权，而不是固定五个方向。

### 28. 为什么攻击预警与实际伤害必须使用同一份锁定数据

**秋招参考答案：**

预警是玩家做决策的契约。前摇开始时应锁定位置、方向、半径和生效时间，复制给客户端画圈、直线或扇形；伤害时使用同一份数据，不能重新追踪玩家，否则玩家已经躲开预警仍被命中。哥布林突进和横扫锁方向，萨满扇形锁发射方向，精英蘑菇菌毯锁地面点，Boss 弹幕只在前摇阶段转向，开始连续发射后不硬追踪。

攻击提前扣血通常是把伤害放在 Ability 激活或 Montage 开始，而不是 Impact 时刻。Aura 使用 WaitDelay/计时器到命中帧后才做权威查询和伤害。

### 29. 精英怪如何做到“不复制一套新蓝图”

**秋招参考答案：**

EncounterVolume 用 EliteSpawnIndices 标记某些出生槽。服务器 Deferred Spawn 敌人时先设置 bEliteVariant 和表现缩放，再进入 BeginPlay，让生命、伤害、速度、攻速、特殊技概率、奖励和碰撞都从统一 EliteEnemy Balance 乘算。bEliteVariant、缩放、韧性和专属技能状态复制给客户端，原种族模型、动画和基础 Ability 继续复用。

这样同一哥布林或蘑菇类可以按房间配置变成精英，不需要维护多个几乎相同的 Blueprint。专属行为仍按“精英 + 种族”判断，避免普通怪误用。

### 30. 精英蘑菇菌毯如何避免持续每帧伤害和跨楼层误伤

**秋招参考答案：**

服务器复制一个包含位置、半径、武装时间和过期时间的状态。到生效时间后，服务器查询范围内玩家，但维护 Victims 集合，同一玩家在同一块菌毯最多命中一次；死亡或过期立即清状态。除了二维半径，还检查玩家与菌毯 Z 差小于阈值，避免楼上玩家被楼下区域命中。

客户端只按服务器时间绘制预警、待激活和生效表现。若要做周期伤害，应显式设计 Tick 间隔和每目标命中计数，而不是在 Actor Tick 中无节制扣血。

### 31. Boss 如何避免随机攻击连续重复或长期不出某种技能

**秋招参考答案：**

先按阶段、距离、视线、冷却、召唤物上限和护盾次数构造合法动作，再做加权选择。额外记录 PreviousAction、连续未出爪击/甩尾/召唤/远程的计数，降低连续重复，并在计数超过阈值时提供保底动作。近距离优先考虑爪击和甩尾，远距离才考虑投掷、冲锋或弹幕；某动作冷却未结束时不能进入候选。

真正成熟的随机系统必须可复现测试。我会把随机源种子注入 Ability，跑数千次统计频率、最大连续次数和每种技能最长空窗，而不是只看一局感觉。

### 32. Boss 为什么在 50% 血量处先 Clamp，再进入转阶段

**秋招参考答案：**

如果一次高伤害把一期 Boss 从 51% 直接打到 0，直接按新生命判断会跳过二阶段。Aura 在生命变化回调中计算阈值，一期伤害达到阈值时把生命设置回阈值，取消当前 Ability、清眩晕、禁用移动并进入 Transitioning。转阶段期间拒绝伤害和控制；计时结束后添加二阶段标签、恢复移动并启用新动作集。

这保证阶段演出和玩法一定发生。更通用的做法是把阶段伤害门槛放进专门的 Execution 或 Boss 状态组件，避免依赖属性回调中的反向 SetBaseValue。

### 33. Boss 护盾为什么在 AttributeSet 的伤害入口处理

**秋招参考答案：**

所有技能最终都通过 GameplayEffect 修改 Health，所以在统一入口处理护盾可以覆盖火球、Q、E、Combo 和后续装备效果，避免每个技能分别判断。当前流程先护甲减伤，再调用 AbsorbBossWardDamage；护盾扣到零时清计时器和表现，超额伤害继续进入生命。

当前 BossWardHealth 是 Enemy 的复制字段，不是 GAS Attribute，优点是实现简单；缺点是 UI、Modifier 和预测不如 Attribute 统一。若未来玩家也有多种护盾，我会改成 Shield Attribute 或 Meta Attribute + ExecutionCalculation。

### 34. 连续火球弹幕为什么不是追踪弹

**秋招参考答案：**

设计目标是“读预警、离开弹道”，不是持续逼迫玩家。Boss 在弹幕前摇阶段可按有限转速朝玩家方向调整，开始通道后锁定 BarrageForward，并按固定间隔与散布生成非追踪投射物。玩家移动后可以躲开后续弹道；AIController 在整个通道期间停止移动和普通转向，避免别的逻辑篡改方向。

网络上只需服务器生成复制投射物和同步 Boss ActionState，不需要每帧复制追踪目标，玩法和带宽都更可控。

### 35. EncounterVolume 的六态为什么比几个 bool 更好

**秋招参考答案：**

六态是 Dormant、Arming、LockedCombat、Cleared、RewardAvailable、Completed。它让每个阶段只有一组合法行为：Dormant 才能触发；Arming 做 1 秒房内驻留；LockedCombat 才刷怪和关门；Cleared 处理一次清场；RewardAvailable 等待宝箱；Completed 禁止重复奖励。若用 bStarted、bLocked、bCleared、bRewarded 等多个 bool，很容易出现互相矛盾的组合。

状态变化由服务器执行，EncounterState、剩余敌人和 ArmingEndServerTime 复制。重复结算由 bRoomClearHandled 和稳定 EncounterId 防护，波次间空窗也不会被验证计时器重复重启。

### 36. 玩家进入房间的判定为什么不能只看触发盒中心

**秋招参考答案：**

房间 Actor 的原点可能在深处，门也可能移动过。Aura 把 TriggerBox 靠近入口的一侧作为基准，并结合物理上位于该房入口附近的 Gate 计算入口平面。玩家越过入口平面约 40uu 后才开始 1 秒驻留；继续向房间深处不会取消，退回门外才重置。这样不会出现玩家还在门外就关门，也不要求站在门坐标上不动。

这类空间判定应在局部坐标中完成，避免房间旋转后世界 X/Y 假设失效。

### 37. 预置怪、地下刷怪和开箱伏击如何共用一套房间逻辑

**秋招参考答案：**

StandingGuardCount 决定开局可见的怪，剩余 SpawnOffsets 在锁门后先播放 0.65 秒预警再生成；Ambush 可按 EnemiesPerWave 分波。开箱伏击的第一阶段清怪后只把状态改为 RewardAvailable，不持久化为最终清房；玩家开箱后重新进入 Arming/LockedCombat，刷第二批怪，第二阶段结束才记录 EncounterId 完成。

所有生成怪都注册同一个 OnEnemyDefeated、剩余数和 HomeTransform，精英槽、奖励归属和越界拉回也复用。关键是阶段一不能提前写“已清房”，否则读档会跳过伏击。

## 第四部分 联机、背包、装备与存档

### 38. Fast Array 比直接复制 TArray 好在哪里

**秋招参考答案：**

普通复制 TArray 变化时可能需要比较或发送整个数组；FFastArraySerializer 给每个 Entry 维护复制键，只发送新增、修改和删除的 Delta。Aura 的 FAuraInventoryEntry 继承 FFastArraySerializerItem，容器实现 NetDeltaSerialize，服务器变更后调用 MarkItemDirty 或 MarkArrayDirty；客户端在 PostReplicatedAdd、PostReplicatedChange 和 PreReplicatedRemove 中统一广播 UI 刷新。

Fast Array 不自动保证业务正确。忘记 MarkDirty 会导致客户端不更新，重排时持有 Entry 指针也可能失效，删除后 UI 必须按稳定槽位或 GUID 重建。

### 39. 为什么背包还要使用 COND_OwnerOnly

**秋招参考答案：**

Fast Array 解决“发多少”，Owner Only 解决“发给谁”。完整背包只有拥有者和服务器需要，广播给其他客户端既浪费带宽，也泄露个人构筑。Aura 把 Inventory Fast Array、个人成长和领取状态限制给 Owner；全体只复制需要共同观察的角色外观、世界掉落和房间状态。

装备外观如果需要他人看到，应另做紧凑的装备摘要，而不是取消背包的 Owner Only。

### 40. 物品 Definition、Instance 和 GUID 分别解决什么问题

**秋招参考答案：**

Definition 是静态共享数据，如 ItemId、名称、图标、类型、槽位和最大堆叠；Instance 是一次具体掉落，包含唯一 GUID、数量、等级、品质、强化、随机词条、随机种子和来源；GUID 标识“这一件”物品。两个同名法杖可以有不同品质和词条，因此不能只靠 ItemId 操作。

存档只保存稳定 DefinitionId 和实例数据，不保存 UObject 指针。加载时通过 Catalog 解析 DefinitionId；若定义已删除或 GUID 重复，验证失败并保护原档。

### 41. 拖拽背包为什么要同时发送 FromSlot、ToSlot 和 ExpectedInstanceId

**秋招参考答案：**

客户端看到槽 0 是物品 A，但请求到服务器前可能因为拾取、堆叠或另一操作而变化。若只发送槽号，服务器可能把后来进入槽 0 的物品 B 移走。ExpectedInstanceId 相当于乐观并发版本：服务器确认来源槽当前仍是 A 才执行，否则返回“物品位置已变化，请重试”。

它不能解决所有并发问题；复杂事务还可加背包 Revision。对当前单拥有者顺序 RPC，GUID 已能阻止最危险的陈旧拖拽。

### 42. 空格移动、交换、部分堆叠和装备不可堆叠的规则如何统一

**秋招参考答案：**

服务器先验证槽位。如果目标为空，只修改来源 SlotIndex；目标非空且 CanStackWith 为真，则转移到目标 MaxStack，来源可能剩余或删除；不能堆叠则交换两个 SlotIndex。Equipment 无论 Definition 中 MaxStackSize 是否误配，都强制 MaxStack 为 1，CanStackWith 也返回 false，因此装备永远交换而不合并。

删除 Entry 要 MarkArrayDirty，数量或槽位变化要 MarkItemDirty。测试应覆盖完整合并、部分合并、满堆拒绝、交换、空移和错误 GUID 拒绝。

### 43. 装备替换怎样避免旧装备丢失

**秋招参考答案：**

装备操作是背包和 EquipmentComponent 的跨组件事务。先检查目标槽和物品合法性；如果已有旧装备，背包侧用新装备所在 Entry 原位换回旧装备，再把新装备交给装备组件；若槽为空则删除背包 Entry。只有两个组件的前置条件都满足才提交，并在完成后刷新唯一一组 GameplayEffect。

若未来逻辑更复杂，我会做显式事务对象：先生成背包和装备的候选快照，全部 Validate 后一次 Commit；任何失败恢复旧快照。不能先 Remove 再希望后续 Add 一定成功。

### 44. 个人掉落怎样保证其他玩家看不到也捡不到

**秋招参考答案：**

服务器为每名合格玩家独立掷骰，WorldItem 记录 ReservedPlayer 和 bExclusiveOwner。独占物把 Actor Owner 设置为该玩家 Controller，并启用 bOnlyRelevantToOwner，所以其他客户端通常不会收到 Actor；服务器 TryPickupBy 仍再次检查 PlayerState 归属、240uu 距离、角色存活和背包容量。客户端隐藏不是安全边界，服务器校验才是。

玩家主动丢弃的装备则立即共享，不启用独占；这样附近列表显示出来时，队友确实可以拾取。

### 45. 为什么世界掉落不使用碰撞自动拾取装备

**秋招参考答案：**

装备有品质和词条，自动拾取会让玩家无选择地塞满背包，也容易在多人时误拿。Aura 只有药剂等消耗品保留走过自动拾取；装备进入 240uu 后显示附近列表，鼠标可选具体物品，或按 F 拾取当前高亮。世界表现使用图标、品质光圈和高亮，真正拾取仍走服务器 RPC。

性能上每人世界掉落有数量上限、6000uu 网络裁剪和 120 秒生命周期，但当前每件 WorldItem 仍有 Tick 和 Billboard/动态表现，是后续性能审计重点。

### 46. Reliable RPC 是否保证交易“恰好执行一次”

**秋招参考答案：**

不保证业务上的恰好一次。Reliable 只保证在连接存续时按序重传和到达，客户端超时重试、UI 双击、重连后重放或服务端处理后响应丢失，仍可能产生重复业务请求。Aura 给交易附加 GUID，服务器记录已处理 ID，重复 ID 不再执行。

更完整的 exactly-once-like 语义需要幂等操作、请求结果缓存、持久事务日志和客户端确认。游戏内通常追求“至少一次传输 + 幂等服务器处理”，而不是宣称网络能天然 exactly once。

### 47. 当前 RequestId 去重实现有什么问题

**秋招参考答案：**

当前每个 PlayerController 用一个 TSet 保存最近请求，重复或无效 GUID 拒绝，数量达到 256 后也拒绝。优点是简单，短局内能防双击和重复 RPC；问题是没有淘汰、时间窗口和结果缓存，长局达到 256 后所有新交易都会失败，重复请求也得不到原结果。

我会改成固定容量 LRU：`RequestId -> {Result, ExpireTime}`，处理前查询；命中则返回缓存结果，未命中才执行业务并写入。或者使用每玩家单调递增序号，保存最近确认窗口。还要区分不同业务域，避免商店请求挤占升级请求。

### 48. OnlineSubsystemNull 的房间流程是什么

**秋招参考答案：**

GameInstanceSubsystem 从 NULL 子系统取得 SessionInterface。Host 创建 `bIsLANMatch=true`、公开连接数 2、允许 JoinInProgress 的会话；成功后 OpenLevel DungeonDemo 并带 `listen`。客户端以 LAN Query 查找带项目键的会话，JoinSession 成功后解析 ConnectString，再 ClientTravel 到房主。

它依赖局域网广播和房主 Listen Server，没有账号、NAT 穿透、平台邀请、云存档和互联网发现。把它写成“多人联机框架”可以，但必须明确“当前可运行边界是局域网双人”。

### 49. Listen Server 和 Dedicated Server 的主要差异是什么

**秋招参考答案：**

Listen Server 既是服务器又有本地玩家和渲染，房主零网络往返、机器性能和作弊权限都更特殊；Dedicated Server 无本地玩家、不渲染，所有客户端都经网络，逻辑更公平也更适合部署。代码不能假设服务器一定有 LocalController、HUD、音频或 PlayerCameraManager。

Aura 用 `GetNetMode() != NM_DedicatedServer` 保护表现，并用 `-server -nullrhi` 做双客户端回归；但当前发行版引擎不能产出可发布的 Server Target，所以“编辑器服务端流程通过”不等于“独立服务端包已交付”。

### 50. 当前项目有没有断线重连，为什么不能把存档说成重连

**秋招参考答案：**

没有完整断线重连。SaveGame 是单机磁盘档，保存成长、背包、装备和关卡进度；局域网联机中的 PlayerState 和世界状态只存在于当前服务器进程。客户端断开再加入时，没有稳定账号 ID 去匹配旧 PlayerState，也没有重连令牌、离线宽限、Pawn 重新绑定和私有状态补发协议。

“死亡后复活”是同一连接内重建或恢复 Pawn；“单机退出重进”是读 SaveGame；“联机掉线重连”需要身份和服务器会话恢复，是三件不同的事。

### 51. 如果要实现 Aura 的断线重连，你会怎么设计

**秋招参考答案：**

客户端加入时由服务器签发 SessionPlayerId 和一次性 ReconnectToken，服务端保留离线玩家快照与过期时间。掉线后 PlayerState 不立即销毁，或将成长、背包、装备、位置、生命法力、当前房间参与状态序列化到服务器 SessionState。重连时认证 Token，找到原身份，重新创建 Controller/Pawn，绑定 PlayerState/ASC，恢复 Owner Only 数据，再发送当前 GameState、Encounter、门、Boss 和个人掉落快照。

事务层还要保存最近请求序号，避免掉线前交易已成功、客户端没收到结果后重发。若房主 Listen Server 退出，当前方案无法恢复；那属于主机迁移或后端权威服务器问题，应另做。

### 52. SaveGame v5 的加载和迁移策略是什么

**秋招参考答案：**

存档保存稳定 ItemId、GUID、数量、等级、品质、词条、来源、成长、背包槽、装备槽、检查点、宝箱、房间和封印。加载时先检查 SchemaVersion 在支持范围内，再校验成长点数守恒、技能前置、物品定义、GUID 唯一、槽位唯一、数量、品质、强化、词条、检查点和封印 ID。旧 v1–v4 按各自旧规则验证后迁移到当前内存结构，例如 v4 的三级火球默认映射到穿透分支。

如果反序列化、校验或迁移失败，设置 DiskWriteBlocked，保留原文件并禁止后续覆盖。合法旧档在内存中迁移，下一次状态变化再写成 v5。

### 53. 为什么迁移必须“先按旧规则校验，再转成新规则”

**秋招参考答案：**

直接用新规则验证旧档会把合法历史状态误判为非法；先迁移再验证又可能让畸形旧数据通过迁移被“洗白”。正确顺序是：根据 SchemaVersion 选择旧版不变量校验，构造候选新结构，再用当前不变量二次校验。两步都通过才加载。

迁移函数应是确定性、幂等和无外部副作用的纯转换。测试要对同一旧档连续加载两次，确认等级、点数、GUID、词条和地图进度不漂移。

### 54. 为什么存档写入要合并 0.35 秒，当前还缺什么

**秋招参考答案：**

背包移动、装备刷新和奖励可能在短时间连续触发。如果每个 OnInventoryChanged 都同步写磁盘，会产生重复序列化和卡顿。Aura 只设置 bSavePending，并在 0.35 秒后统一 Capture + Validate + SaveGameToSlot；退出或关键旅行前显式 Flush。

当前仍不是严格原子写：若底层写入中断，仍可能损坏槽。生产方案会写临时槽、校验后原子替换，并保留上一版本备份；大档还应异步写入，主线程只生成不可变快照。

### 55. 联机中哪些状态依靠复制，哪些依靠 RPC

**秋招参考答案：**

持续状态用复制：属性、死亡、成长摘要、Fast Array 背包、装备、房间状态、门、封印、Boss 阶段、预警数据。一次性客户端意图用 Server RPC：拾取、拖拽、使用、交易、祭坛和升级。只给某个玩家的结果提示用 Client RPC；短暂表现可用 Multicast 或由 RepNotify 根据状态生成。

原则是“状态最终以复制收敛，RPC 只表达事件或请求”。不能只靠一次 Multicast 表示永久门状态，因为晚加入客户端收不到过去的事件。

### 56. 晚加入客户端如何得到当前房间和 Boss 状态

**秋招参考答案：**

EncounterState、RemainingEnemyCount、门状态、BossPhase、BossActionState、护盾和 GameState 任务数据都是复制属性，新客户端建立 Actor Channel 后会收到当前值，而不依赖过去的“开始战斗”事件。OnRep 刷新视觉；房间还可对新 Controller 调 SyncStateToController，补发当前目标文字。

一次性特效不必重播，但持续预警必须包含服务器时间、结束时间和锁定几何，使晚加入者能计算剩余阶段。只 Multicast 一个“播放 4 秒特效”不足以支持晚加入。

## 第五部分 测试、性能与工程化

### 57. 你为 Aura 做了哪些自动验证，分别能证明什么

**秋招参考答案：**

验证分四层。第一层是数据和地图静态校验，检查战斗数值约束、物品目录、掉落表、路线奖励和关卡 Actor 引用；第二层是进程内 Exec 烟测，触发真实 Ability、碰撞、房间和背包路径并检查日志标记；第三层是跨进程测试，例如先写独立 Save Slot，再启动新进程验证恢复和幂等；第四层是服务端加两个真实客户端，验证 Owner Only、房间、封印、个人掉落和交易。

网络烟测还使用 PktLag 100/200ms 与 PktLoss 1%/3%。Cook 和 Development/Shipping 构建证明资产依赖与打包链路能通过。它们不能证明画面手感、长期稳定性、真实公网 NAT、峰值性能或玩家理解度，所以不能把“烟测通过”说成“产品验收完成”。

### 58. 延迟和丢包测试为什么不能只看“客户端没崩溃”

**秋招参考答案：**

要验证业务不变量，而不仅是进程存活。购买场景发送同一个 RequestId 两次，服务端和两个客户端都应看到只扣一次魂、只增加一件物品；Combo 场景要验证个人标记在延迟下可见且只消费一次；封印场景要验证共享计数和门状态最终一致。脚本还检查引擎日志确实应用了指定 PktLag/PktLoss，避免测试参数没有生效。

仍应补充 RTT 分布、请求完成时间、可靠队列积压、断开率和长时间重复操作；固定 1%/3% 丢包只是回归档位，不代表所有网络条件。

### 59. 你能否说“项目已经完成性能优化”

**秋招参考答案：**

不能。当前有一些结构性措施：AIController 0.1 秒 Tick、MoveTo 0.22 秒节流，投射物仅在追踪或环绕时 Tick，个人掉落有数量上限、生命周期和 NetCullDistance，背包使用 Fast Array + Owner Only，很多关卡 Actor 不 Tick。但项目尚没有一份基于目标硬件、固定场景和稳定版本的 Game/Render/GPU/Network 基线报告，所以只能说“做了初步性能约束”，不能说优化完成。

真正的结论需要给出目标，例如 1080p 60 FPS、Game Thread P95、GPU P95、内存峰值和带宽，并用 Unreal Insights、stat unit、ProfileGPU、Network Insights 和 MemReport 复测前后差异。

### 60. 当前最值得优先审计的 Tick 热点有哪些

**秋招参考答案：**

第一是每个敌人同时有 Enemy 0.08 秒 Tick 和 AIController 0.1 秒 Tick，且无目标时主动找玩家；第二是 WorldItem 每帧旋转、浮动、取 PlayerCameraManager 并调整图标/光圈；第三是 PlayerController 每帧处理瞄准、附近掉落、交互高亮和墙体遮挡；第四是 Character 每帧做相机插值和火球转身。

优化顺序是先用 Insights 证明占比，再改事件驱动：静止世界物品只在高亮或相机显著变化时更新，远处掉落停 Tick；AI 共享目标列表并降低非战斗更新频率；交互对象用 Overlap 注册候选而非反复遍历；相机参数达到目标后停插值。不能凭直觉把所有 Tick 一刀切掉。

### 61. 如果同屏从 10 只怪增加到 100 只，最先可能出问题的是什么

**秋招参考答案：**

CPU 侧可能先出现 AI 决策、路径请求、碰撞查询、动画更新和每怪两个 Tick 的开销；网络侧会增加 CharacterMovement、属性、ActionState 和投射物复制；GPU 侧是骨骼蒙皮、阴影、Niagara 和透明预警过绘。大量同时 MoveTo 还会让寻路和避障抖动。

我会建立 10/30/60/100 怪阶梯场景，记录 Game Thread、Anim、Navigation、Physics、GPU、Actor Channel 和字节率。方案包括 AI LOD、分帧更新、攻击令牌限制、Mass/群组移动、动画预算分配器、对象池、关阴影、特效 LOD、Replication Graph 和相关性裁剪。先优化真实瓶颈，而不是直接上复杂框架。

### 62. 如何优化联机带宽，而不破坏玩法一致性

**秋招参考答案：**

先按状态重要性分类。背包和成长 Owner Only；世界任务全体复制但低频；预警只复制动作类型、锁定几何和服务器时间，不复制每帧特效；投射物用服务器生成和移动复制，但大量弹幕可改为初始状态 + 客户端确定性模拟；位置使用量化类型；频繁小状态合并到紧凑结构；远处 Actor 依赖 NetCullDistance 或 Replication Graph。

还要减少无意义 ForceNetUpdate。它应在关键状态转移时使用，不能每帧强推。优化后以每连接字节率、Actor Channel 数和丢包下的队列延迟验证，不只看包体大小。

### 63. Niagara、半透明光圈和墙体淡化有哪些 GPU 风险

**秋招参考答案：**

半透明通常不能写入普通深度并按像素混合，重叠越多，Overdraw 越高；大面积光圈、光柱、弹幕和墙体淡化会大量覆盖屏幕。Niagara 还可能有粒子模拟、排序、灯光和材质指令成本。Aura 已删除装备光柱，但每件装备仍有 Billboard、光圈和灯光，Boss/房间预警也可能叠加。

我会用 Shader Complexity、Quad Overdraw 和 ProfileGPU 检查，限制屏幕覆盖、粒子数和动态灯，做距离 LOD；能用 Masked 就不强用 Translucent；同材质实例化并减少材质切换。墙体淡化还要注意创建过多 MID 和恢复原材质的生命周期。

### 64. 你如何用 Unreal Insights 定位一次掉帧

**秋招参考答案：**

先固定地图、相机、怪物数和操作脚本，分别记录空场与战斗 Trace。用 Frame 视图判断瓶颈在 Game、Render、RHI 还是 GPU；若是 Game Thread，展开 Tick、AI、Navigation、Ability、GC 和碰撞 Scope；若是 Render/GPU，再看 Draw、阴影、Niagara、Translucency。对网络卡顿同时开 Network Insights，对周期尖峰检查 GC、资产流送和同步 SaveGame。

找到热点后只做一个改动，重复相同场景，比较平均值、P95/P99 和峰值，不只看一次 FPS。最终把测试硬件、版本、参数和 Trace 文件记录下来，结论才可复现。

### 65. Cook 阶段暴露了编辑器中没有出现的动画问题，说明了什么

**秋招参考答案：**

编辑器环境可能加载额外模块、保留未 Cook 数据或容忍动态构建，而打包后的运行时只包含被引用且可序列化的资源。Aura 曾遇到原生 AnimNode 在 Cook 构建中 NodeData 为空的断言，改为可 Cook 的 BlendSpace 节点加 DefaultSlot 叠加后通过。这个问题说明“Editor 编译成功”不等于“Cook 和包体可运行”。

发布门槛至少包括 Development/Shipping Cook、干净机器启动、核心流程、资源引用审计和日志警告分类。自动 `-nullrhi` 启动不等于有画面的完整通关。

## 第六部分 C++ 与 Unreal Engine 底层

### 66. UObject 为什么通常不能用 `std::shared_ptr` 管理

**秋招参考答案：**

UObject 的生命周期由 UE 垃圾回收和对象系统管理，GC 从 Root、UPROPERTY、AddReferencedObjects 等引用图判断可达性；`std::shared_ptr` 的引用计数不在这张图里，也不能代替 UObject 的创建、反射和销毁协议。UObject 应使用 UPROPERTY/TObjectPtr 持有强引用，非拥有观察用 TWeakObjectPtr，需要长期保活可显式 Root，但要谨慎解除。

TSharedPtr 适合非 UObject 的普通 C++ 对象，例如 OnlineSessionSearch。两套生命周期不能混用。

### 67. TObjectPtr、TWeakObjectPtr、TSharedPtr 和裸指针如何选择

**秋招参考答案：**

TObjectPtr 用于 UObject 所有者中的反射强引用，能被 GC 跟踪；TWeakObjectPtr 不阻止 UObject 回收，访问前检查 IsValid，适合目标、临时交互对象和计时器捕获；TSharedPtr 是普通 C++ 引用计数所有权；裸指针只适合短期、明确受外部生命周期保护且不需要反射的访问。

Aura 中锁定敌人、ActiveVendor、掉落候选使用弱引用；组件和资产成员用 TObjectPtr；FOnlineSessionSearch 用 TSharedPtr。若把敌人用裸指针跨帧保存，Actor Destroy 后就可能悬空。

### 68. RAII 与 UE GC 是什么关系

**秋招参考答案：**

RAII 是 C++ 对象构造时获取资源、析构时释放资源，适合文件句柄、锁、内存、作用域预测窗口等；UE GC 只解决 UObject 内存可达性，不会自动帮我注销委托、清外部句柄或回滚事务。两者互补。

例如 FScopedPredictionWindow 用 RAII 约束预测键作用域；SessionSubsystem 在 Deinitialize 中清 DelegateHandle；Actor 的 Timer 通常随 World 清理，但捕获外部对象仍要用弱引用。不能因为对象受 GC 管理就忽略资源释放。

### 69. 基类为什么通常需要虚析构函数

**秋招参考答案：**

如果通过基类指针 delete 派生对象，而基类析构非 virtual，会产生未定义行为，派生资源可能不释放。含其他虚函数且作为多态接口的普通 C++ 基类通常应有虚析构。UE 的 UObject/Actor 不由用户直接 delete，而由引擎生命周期管理，但普通辅助接口和非 UObject 层仍遵守这条规则。

虚函数通常通过对象内的 vptr 查 vtable 间接调用，有一次间接跳转并可能阻碍内联；性能关键的大批量对象可考虑组合、模板或数据导向设计，但不应为微小成本牺牲正确性。

### 70. C++ 对象内存布局受哪些因素影响

**秋招参考答案：**

成员声明顺序、类型对齐、填充、继承、虚函数指针和 ABI 都会影响 `sizeof`。编译器会在成员间和尾部插 Padding，使数组中每个对象满足对齐。把大对齐成员放前面、按大小分组有时能减小结构体，但 UE 反射结构还要考虑序列化兼容，不能随意重排已持久化字段。

缓存角度更重要的是热数据是否连续。100 个 AI 每帧只需要位置、状态和下次决策时间，却遍历庞大 Actor 对象，会造成缓存未命中；这也是 Mass/ECS 数据布局能扩展的原因。

### 71. 移动语义解决什么问题，`std::move` 本身会移动吗

**秋招参考答案：**

移动语义允许把临时对象拥有的资源转交给新对象，避免深拷贝。`std::move` 只是把表达式转换为右值引用，不执行移动；是否真正移动由目标类型的移动构造/赋值决定。移动后对象仍必须可析构、可赋值，但值通常未指定。

UE 的 TArray、FString 等也支持 MoveTemp。对很小或隐式共享对象，移动收益可能有限；对 UObjects 不能靠移动对象本体改变引擎身份。

### 72. `TArray` 增删时为什么不能长期保存元素指针

**秋招参考答案：**

TArray 扩容会重新分配连续内存，RemoveAt 会移动后续元素，因此旧地址和引用可能失效。Aura 的背包 TryMoveItem 在修改数组前查 Entry 指针，删除来源时随后不再使用该指针；复杂逻辑更安全的方式是保存 Slot/GUID 或 Index，并在结构变化后重新查找。

稳定身份应由物品 GUID 提供，而不是元素内存地址。需要地址稳定可考虑间接存储，但会牺牲局部性和增加分配。

### 73. 哈希表的平均 O(1) 为什么不是绝对 O(1)

**秋招参考答案：**

散列表平均查找是 O(1)，前提是哈希分布良好、装载因子受控；最坏情况下大量冲突会退化到 O(n)，扩容本身也可能是 O(n)。TMap/TSet 还会有哈希计算、随机内存访问和额外内存开销，小数据量时线性 TArray 可能更快。

Aura 的最近请求只有最多数百项，TSet 便于查重；若做有序过期 LRU，还需要 TMap 加双向链表或环形队列，而不是只看理论复杂度。

### 74. 缓存行和伪共享是什么

**秋招参考答案：**

CPU 以缓存行为单位搬运数据，常见为 64 字节。两个线程即使修改不同变量，只要它们位于同一缓存行，也会反复让对方缓存失效，形成伪共享。解决方式包括按线程分片、合并写入、把高频写变量分离或按缓存行对齐。

UE 大多数 Gameplay Actor 逻辑在 Game Thread，不会直接出现多线程写同一 AI 状态；但在 TaskGraph、Mass 或自建并行模拟中必须考虑。先用分析工具证明，不要盲目 padding 所有结构。

### 75. UE 反射系统为 `UCLASS`、`USTRUCT`、`UPROPERTY` 做了什么

**秋招参考答案：**

UnrealHeaderTool 在编译前解析这些宏，生成类型注册、属性元数据、序列化、GC 引用、蓝图暴露、RPC 和复制所需代码。GENERATED_BODY 把生成声明接入类型。普通 C++ 编译器本身并不知道 `ReplicatedUsing` 或 BlueprintCallable 的语义。

因此新增复制属性不仅要写 UPROPERTY(Replicated)，还要在 GetLifetimeReplicatedProps 注册；RPC 需要 UFUNCTION(Server/Client/NetMulticast, Reliable/Unreliable) 和 `_Implementation`。忘记任何一环都会出现“能编译但不复制”或 UHT 错误。

### 76. Actor 从生成到销毁的关键生命周期是什么

**秋招参考答案：**

常见顺序包括构造函数创建默认子对象、OnConstruction 处理实例构造、PreInitializeComponents、PostInitializeComponents、BeginPlay、Tick、EndPlay，最后由 GC 回收。Deferred Spawn 会先 SpawnActorDeferred，让调用方在 Construction/BeginPlay 前注入参数，再 FinishSpawning。

Aura 对精英敌人和世界物品使用 Deferred Spawn，因为精英标志、品质、归属等必须在 BeginPlay 初始化属性和视觉前确定。不能在构造函数访问依赖 World 或已加载运行时内容的状态。

### 77. `BeginPlay`、`PossessedBy/OnPossess` 和 `OnRep_PlayerState/OnRep_Pawn` 分别适合做什么

**秋招参考答案：**

BeginPlay 表示 Actor 已进入世界，但客户端 PlayerState 或 Pawn 复制时序未必完整；服务器 PossessedBy/Controller OnPossess 适合权威绑定 Pawn、初始化能力和成长；客户端 OnRep_PlayerState 或 Controller OnRep_Pawn 用于复制到达后重新初始化 ASC、输入上下文和 UI。

网络代码不能只在 BeginPlay 假设 Controller、PlayerState 和 HUD 都存在。初始化函数应可重复调用且幂等，分别从服务器和客户端正确入口触发。

### 78. Actor Ownership、Role 和 Relevancy 有什么区别

**秋招参考答案：**

Ownership 表示网络拥有链，决定哪个客户端能发送该 Actor 的 Server RPC，也用于 Owner Only 条件；Role 描述本机对 Actor 的权威或代理身份，服务器是 Authority，客户端通常是 AutonomousProxy 或 SimulatedProxy；Relevancy 决定服务器是否给某连接建立/维持 Actor Channel。

Aura 的个人 WorldItem 把 Owner 设为玩家 Controller，并 OnlyRelevantToOwner；这既减少可见范围，也让归属语义清晰。但服务器拾取函数仍校验 ReservedPlayer，不能把 Relevancy 当权限控制。

### 79. RepNotify 是否保证按业务依赖顺序执行

**秋招参考答案：**

不能依赖不同属性 OnRep 的业务顺序。属性可能同帧到达，但回调顺序不应作为协议；Actor 引用也可能尚未解析。若状态存在强依赖，应合并到同一个复制结构，或在 OnRep 中检查依赖是否就绪并调用一个幂等 Refresh 函数。

Aura 的 Boss ActionState 把动作、位置和半径放在同一结构中，客户端按结构刷新预警，比三个独立属性更安全。UI 刷新也应从当前完整状态重建，而不是假设“先收到品质再收到物品”。

### 80. Reliable RPC 太多会发生什么

**秋招参考答案：**

可靠 RPC 会重传并按序处理。一个包丢失时，后续同通道可靠消息可能等待，形成队头阻塞；持续高频发送还会挤满可靠缓冲，严重时断开连接。每帧位置、特效或瞄准更新不应使用 Reliable。

交易、使用物品和关键确认适合 Reliable；高频表现、伤害飘字或可由状态重建的提示适合 Unreliable/属性复制。最终一致状态应由复制保证，不能为了“保险”把所有事件都改 Reliable。

### 81. GameplayTag 相比枚举或 bool 的优势是什么

**秋招参考答案：**

Tag 是层级化、可组合、可由 Effect 授予和查询的运行时标签。`State.Stunned`、`State.InCombat`、`Cooldown.Shock` 可以被多个系统统一观察，Ability 也能声明阻止/取消关系；比在 Character 上增加大量互不协调的 bool 更易扩展。层级查询还能让 `State.CrowdControl` 统摄多个子状态。

缺点是字符串注册错误和过度自由。关键 Tag 应集中声明或在启动校验，区分 HasTag 和 HasTagExact，并避免用 Tag 替代需要数据载荷的状态结构。

### 82. 委托和 Timer 最常见的生命周期 Bug 是什么

**秋招参考答案：**

对象销毁后委托仍回调、Lambda 捕获裸 this、重复绑定导致执行多次、Timer 在状态切换后仍落地旧伤害。UObject 成员函数通过 AddUObject 通常能感知对象生命周期，但仍要在 EndPlay/Deinitialize 解除长期外部委托；Lambda 应捕获 TWeakObjectPtr 并检查有效性；进入新状态时清旧 Timer。

Aura 的延时测试和表现清理大量使用 Weak 指针；Boss 死亡、转阶段、眩晕和取消 Ability 时会清攻击计时器。现场排查“特效一直播放”时，我会先查组件 AutoDestroy、Timer 是否清理、Ability End 是否执行和远端 OnRep 是否再次激活。

### 83. 游戏线程能否直接把耗时任务放到后台线程

**秋招参考答案：**

可以把纯计算、文件压缩或不触碰线程不安全 UObject 的工作放到 TaskGraph/线程池，但大多数 Actor、Component、World、Slate 和 UObject 修改要求 Game Thread。正确方式是后台计算不可变输入，完成后切回 Game Thread 提交结果，并用弱引用确认对象仍存在。

例如大规模装备种子模拟可以并行计算数值，但生成 Actor、应用 GameplayEffect 和更新 UMG 必须回主线程。异步不自动更快，任务粒度太小会被调度成本抵消。

## 第七部分 操作系统、网络与图形学

### 84. 进程与线程的区别是什么

**秋招参考答案：**

进程拥有独立虚拟地址空间和系统资源，是隔离与保护边界；同进程线程共享地址空间、代码和大部分资源，但各自有栈、寄存器和调度上下文。线程通信快但更容易产生数据竞争，进程通信通常需要管道、共享内存或 Socket。

Aura 的双客户端回归启动服务端和两个独立 UE 进程，这能验证真实序列化与网络路径；PIE 单进程多窗口不能完全替代跨进程测试。

### 85. Mutex、Semaphore、SpinLock 和原子变量如何选择

**秋招参考答案：**

Mutex 提供互斥，等待时通常会阻塞线程；Semaphore 表示有限数量资源，可允许多个持有者；SpinLock 在短临界区忙等，等待稍长就浪费 CPU；原子适合简单计数和无锁状态，但正确内存序很难。选择取决于临界区长度、争用概率、是否允许睡眠和公平性。

游戏主循环更应减少共享可写状态，通过任务分片和消息提交避免锁。不能为了“无锁”写出难验证的数据结构。

### 86. 什么是虚拟内存和缺页中断

**秋招参考答案：**

每个进程看到连续虚拟地址，页表把虚拟页映射到物理页或后备存储。访问尚未映射、权限不符或不在物理内存的页会触发 Page Fault；轻微缺页可建立映射，严重缺页需要磁盘读取，代价很高。TLB 缓存最近的页表映射。

游戏中的大资源首次访问、内存映射文件和工作集抖动都可能产生尖峰。优化不仅看总内存，还看访问局部性、流送时机和是否在战斗帧同步加载。

### 87. 栈和堆的主要区别是什么

**秋招参考答案：**

栈由线程维护，函数进入退出按帧分配回收，速度快、局部性好但容量有限；堆支持动态大小和跨作用域生命周期，分配更灵活但有分配器开销、碎片和所有权问题。递归过深或大数组放栈会溢出，频繁小堆分配会影响性能。

UE 的 UObject 通常由引擎对象分配管理，TArray 的元素缓冲在堆上。性能敏感循环应复用容器、Reserve 容量或使用池化，但不能牺牲清晰所有权。

### 88. TCP 和 UDP 的差异，动作游戏为什么常用 UDP

**秋招参考答案：**

TCP 提供面向连接、可靠、有序字节流和拥塞控制，但丢包会造成流内队头阻塞，没有消息边界。UDP 是无连接数据报，不保证到达、顺序或去重，但应用可以按消息重要性自定义可靠性、顺序、频率和丢弃策略。实时游戏通常希望旧位置包丢了就用新包，不必等重传。

UE 游戏复制在 UDP 之上实现 Channel、序号、Ack、可靠 Bunch 等机制。登录、下载和后台服务仍可能使用 TCP/HTTP；不是“游戏全部用 UDP”。

### 89. 如何在 UDP 上实现可靠传输

**秋招参考答案：**

给消息或包编号，接收端返回 ACK/ACK 位图，发送端保留未确认窗口并按超时重传；用序号去重和恢复顺序，再加拥塞/速率控制。不同消息可选可靠有序、可靠无序或不可靠最新值。还要处理序号回绕和 MTU 分片。

业务幂等仍在更高层处理。即使网络层不重复交付，客户端业务重试也可能让同一购买请求再次出现。

### 90. 客户端预测、服务器校正和插值分别解决什么问题

**秋招参考答案：**

本地玩家输入若等服务器返回才移动会有一个 RTT 延迟，所以客户端先预测执行并保存输入序列；服务器回传权威状态后，客户端丢弃已确认输入，从权威状态重放未确认输入，叫 reconciliation。其他玩家没有本地输入，通常缓存服务器快照并在稍过去的时间线上插值，平滑抖动；短时间缺包可外推，但误差会累积。

GAS 的 LocalPredicted 解决技能激活层面的即时反馈；投射物命中和伤害仍以服务器为准。两类预测不能混为一谈。

### 91. 客户端和服务器的时间如何对齐预警

**秋招参考答案：**

服务端复制绝对的 ServerWorldTime 或动作开始/结束服务器时间，客户端通过 GameState 的 ServerWorldTimeSeconds 估算当前服务器时间，再计算剩余时长。不要只发送“持续 0.8 秒”并从本地收到包时开始，因为不同延迟玩家看到的命中时刻会不同。

Aura 的房间 ArmingEndServerTime 和持续区域的 Armed/ExpireServerTime 已采用这类思路。还要处理时钟估计跳变，以 Clamp 或平滑避免 UI 倒计时倒退。

### 92. 从模型到屏幕的基本渲染流水线是什么

**秋招参考答案：**

顶点从模型空间经 Model、View、Projection 变换到裁剪空间，做齐次除法得到 NDC，再映射到屏幕；图元装配、裁剪和光栅化产生片元，片元着色计算材质和光照，经过深度、模板、混合等测试写入目标。现代引擎还包含可见性剔除、阴影、GBuffer、后处理和 Temporal Upsampling。

回答时要说明法线不能简单用同一个非均匀缩放矩阵，通常用逆转置矩阵；透视除法在裁剪后进行。

### 93. Z-Buffer 为什么会 Z-Fighting，如何缓解

**秋招参考答案：**

透视投影下深度精度非线性，更多精度集中在近裁剪面附近；两个几乎共面的表面量化到相近深度值会交替通过测试，形成闪烁。把 Near Plane 设得过小会浪费远处精度。

缓解方法包括增大 Near Plane、避免共面几何、使用 Depth Bias、调整网格层级、采用反向 Z 和浮点深度。Aura 的装备图标与光圈曾随视角互相遮挡，本质还涉及两个面在相机方向上交叉；最终把光圈当作相机平行的独立后景层并保持固定深度偏移，而不只调整 TranslucentSortPriority。

### 94. 延迟渲染与前向渲染的主要取舍是什么

**秋招参考答案：**

延迟渲染先把几何属性写入 GBuffer，再按灯光计算，适合大量动态光，材质与光照解耦；代价是显存带宽和 GBuffer 占用，MSAA 与透明物体处理更复杂。前向渲染在一次着色中计算光照，带宽更低、MSAA 和透明更直接，但很多灯会增加每物体/像素成本，需要光源裁剪或 Forward+。

UE 项目选型还受平台、VR、材质特性和 Lumen/Nanite 支持影响，不能只用“灯多就延迟”一句话决定。

### 95. Draw Call 为什么贵，如何减少

**秋招参考答案：**

Draw Call 涉及 CPU 构建命令、状态切换和驱动/RHI 提交，很多小网格会让 CPU 成为瓶颈。减少方式包括材质和网格合批、Instanced Static Mesh/HISM、减少材质槽、LOD、剔除和 Mesh Draw Command 缓存。Nanite 能改善几何提交和 LOD，但不能自动消除所有材质、透明和动态对象成本。

地牢重复墙体、地板和装饰适合实例化；角色、动态门和独特交互物不能盲目合批。要同时关注 GPU 顶点/像素成本，不能只追求最低 Draw Call。

### 96. 为什么半透明对象排序经常出现“视角一变遮挡关系就变”

**秋招参考答案：**

半透明通常按对象或 Bounds 到相机的距离排序，而不是对每个像素做完整顺序无关透明。两个相交或距离接近的透明面无法用单一对象顺序在所有视角正确绘制，所以相机移动时会翻转。TranslucentSortPriority 能强制对象级顺序，但如果几何真正交叉，仍可能露出问题。

解决应从几何关系入手：让背景光圈始终沿相机平面位于图标后方，或把两者合成一个材质/Widget；必要时使用 Masked、CustomDepth 或顺序无关透明方案，同时评估成本。

## 第八部分 算法与系统设计现场题

### 97. A* 与 Dijkstra 的区别是什么，NavMesh 寻路为什么常用 A*

**秋招参考答案：**

Dijkstra 按起点累计代价 `g(n)` 扩展，能求非负权图最短路；A* 按 `f(n)=g(n)+h(n)` 扩展，若启发函数不高估真实剩余代价，则仍能得到最优路径，并因目标方向信息扩展更少节点。`h=0` 时 A* 退化为 Dijkstra。

NavMesh 把可走空间切成多边形图，常用欧氏距离作为启发。得到多边形路径后还需 Funnel/String Pulling 平滑拐点，动态障碍和局部避障另由运行时系统处理。

### 98. 现场写一个背包移动的服务器校验流程

**秋招参考答案：**

```cpp
Result MoveItem(int from, int to, Guid expected, int expectedRevision)
{
    if (!ValidSlot(from) || !ValidSlot(to) || from == to) return Invalid;
    if (expectedRevision != InventoryRevision) return Stale;
    Entry* src = FindBySlot(from);
    if (!src || src->Id != expected) return Stale;
    Entry* dst = FindBySlot(to);

    Candidate next = MakeCandidateSnapshot();
    if (!dst) next.Move(from, to);
    else if (CanStack(*src, *dst)) next.MergeUpToMax(from, to);
    else next.Swap(from, to);

    if (!next.ValidateUniqueIdsAndCapacity()) return Invalid;
    Commit(next);
    ++InventoryRevision;
    MarkFastArrayDirty();
    return Success;
}
```

重点不是语法，而是客户端只发意图、服务器验证陈旧状态、候选快照通过不变量后一次提交。Aura 当前使用 ExpectedInstanceId，没有全局 Revision；这是可以继续增强的地方。

### 99. 如何实现 Boss 加权随机且防连续重复

**秋招参考答案：**

先过滤不合法动作，再动态调整权重：上一次动作权重乘较小系数，连续未出现的动作按计数增加权重，达到保底阈值时直接选择；最后在总权重区间内采样。伪代码如下：

```text
candidates = FilterByPhaseDistanceLOSAndCooldown(allActions)
for action in candidates:
    weight = baseWeight[action]
    if action == previous: weight *= repeatPenalty
    weight *= 1 + starvationCount[action] * starvationBonus
if any starvationCount >= hardPity: choose oldestStarved
else choose WeightedRandom(candidates)
update previous and starvationCount
```

测试应注入固定随机种子，统计分布、最大连出次数和最长空窗；不能只断言每种动作“至少出现过一次”。

### 100. 设计一个有过期时间的请求去重缓存

**秋招参考答案：**

使用 `unordered_map<RequestId, Node>` O(1) 查找，双向链表按最近访问排序；Node 保存业务类型、结果、完成时间和链表迭代器。请求到达时，若命中且未过期，直接返回缓存结果；未命中则执行事务、存结果并放到表头。超过容量或过期时从尾部淘汰。并发服务端还要按玩家或会话加锁/串行化。

若客户端有稳定连接，递增序列号更简单：服务器保存最大连续确认号和一个有限乱序窗口。无论哪种方案，都要缓存“成功和确定性失败”的结果，避免重试表现不一致。

### 101. 附近掉落列表从遍历全世界优化到可扩展方案

**秋招参考答案：**

小规模可用 OverlapSphere 或维护进入 PickupSphere 的候选集合；更大规模使用均匀网格、四叉树或引擎 Spatial Acceleration，按玩家所在格和邻格查询，再做距离和归属过滤。列表只需最近 6 件，可维护大小为 6 的最大堆，复杂度从全排序 O(n log n) 降为 O(n log 6)，或 n 很小时直接线性选择。

更新不必每帧：玩家移动超过阈值、掉落增删或 5–10Hz 定时刷新即可。鼠标悬停目标可单独射线，不要为 UI 每帧遍历所有掉落。

### 102. 设计断线重连状态机

**秋招参考答案：**

客户端状态可为 Connected → SuspectedLost → Reconnecting → Resyncing → Playing/Failed；服务器玩家槽为 Active → GracePeriod → Rebound/Expired。进入 GracePeriod 时冻结或让 AI 接管 Pawn，保存请求序号和个人快照；重连认证成功后重绑 Controller，先发全量基线，再接收基线版本之后的增量，最后开放输入。

Resync 包至少含 PlayerState、背包/装备、ASC 长期状态、位置、生命法力、当前 Encounter、门、Boss、共享任务和个人世界掉落。每份快照带 SessionEpoch/Revision，旧会话消息必须丢弃。房主掉线属于主机迁移，不在普通客户端重连范围内。

### 103. 如何设计原子存档与回滚

**秋招参考答案：**

在 Game Thread 生成不可变、已验证且带版本/校验和的快照；后台写 `slot.tmp`，Flush 后重新读回校验；把当前正式档改名为 `.bak`，再原子替换临时档为正式档。启动时优先验证正式档，失败再验证备份；迁移只在内存候选上执行，成功前绝不覆盖来源档。

还应记录构建版本、schema、保存时间和迁移日志。多人账号存档需要服务端数据库事务和并发版本号，不能直接复用本地 SaveGame 文件策略。

### 104. 如何系统测试 Encounter 状态机

**秋招参考答案：**

先列合法转移表和每态不变量，再做表驱动测试。例：Dormant 门开且无动态怪；Arming 未到时间不能刷怪；退回门外回 Dormant；LockedCombat 门关且剩余数非负；最后一只怪死亡只结算一次；RewardAvailable 重复开箱无奖励；Completed 再触发无效果。还要覆盖生成失败、波次空窗、玩家死亡、晚加入、存档重载和开箱伏击两阶段。

属性测试可随机生成进入/离开/击杀/重连事件序列，持续检查“奖励最多一次、状态不回退到非法阶段、Remaining 不为负”。

### 105. 从 n 件物品中找最近的 k 件，怎么做

**秋招参考答案：**

k 很小且 n 不大时，用大小为 k 的最大堆：遍历每件物品，堆未满就加入；距离小于堆顶时替换，时间 O(n log k)、空间 O(k)。如果只调用一次也可用 `nth_element` 平均 O(n)，再对前 k 排序。n 极小直接排序最简单，工程上应优先可读性。

Aura 附近列表最多 6 件，还要先按本地可见、归属和拾取距离过滤。距离可比较平方，避免不必要开方。

### 106. 如何判断一个目标是否位于扇形攻击内

**秋招参考答案：**

先取二维偏移 `d = target - origin`，检查 `|d|² <= radius²`；再归一化 d，与锁定前向 f 做点积，若 `dot(f,d) >= cos(halfAngle)` 则在扇形内。还要检查高度差、目标存活和碰撞遮挡。点积避免求实际角度。

命中和预警必须使用同一 origin、forward、radius、halfAngle。若目标有胶囊体积，可把边界扩张目标半径，或做扇形与胶囊更精确相交。

### 107. 设计一个性能友好的韧性回复系统

**秋招参考答案：**

当前少量敌人可在 Enemy Tick 中检查“最后受击时间 + 回复延迟”，再按 DeltaTime 回复。规模扩大后，不需要满韧性敌人 Tick：受击时把敌人注册到服务器 PoiseRecoveryManager 的最小堆或时间轮，到回复开始时激活低频批量更新；回满后移除。破韧时单独记录免疫结束时间。

客户端无需高频复制每个小数变化，可量化成百分比并降低更新率，破韧、重置和 UI 可见时再强制更新。

### 109. 项目目前最大的技术欠债是什么

**秋招参考答案：**

一是 PlayerController 体积过大，输入、UI、交互、相机和大量 Smoke Exec 混在一起，应拆成 Targeting、Interaction、UI Presenter 和测试模块；二是 AI 与 Enemy 逻辑集中在 Tick 和大 Ability 中，扩展性有限；三是交易去重只有固定 TSet，没有 LRU 和结果缓存；四是性能尚无正式基线；五是联机只到 LAN，没有稳定身份和重连。

我会按风险先做可观测性与性能基线，再拆业务边界和请求协议，最后扩平台会话。只做类拆分但没有测试保护，容易引入回归。

### 110. 讲一个你做错过的设计，以及如何修正

**秋招参考答案：**

可以讲最初把怪物追击限制绑定到出生点硬半径，结果玩家在边界附近时 AI 在追击与回巢之间反复切换。错误在于把“巢穴归属”误当成“战斗持续条件”，且没有滞回。通过记录状态转移和位置后，我把已有目标的持续条件改成怪物到玩家的视野范围，真正丢失后再回 Home，并增加对应自动回归。

重点不是把自己说得从不犯错，而是展示可复现现象、错误假设、修复原则和防回归证据。

### 111. 如果面试官指出当前代码存在缺陷，你应该怎么回应

优秀回答是“证据 + 取舍 + 可执行修复”，不是态度表演。

### 112. 现场遇到“客户端看到命中，但服务器没扣血”如何排查

**秋招参考答案：**

先分层打点：输入是否触发、Ability 是否激活、TargetData 是否到服务端、Commit 是否成功、服务端是否生成投射物、碰撞回调是否在 Authority 执行、Target ASC 是否存在、EffectSpec 是否有效、PreGameplayEffectExecute 是否因免疫/护盾返回、Health 是否变化、复制是否到客户端。用 NetMode、Role、PredictionKey、CastId、Actor 名称和时间统一日志。

若本地只有特效，那可能只是预测表现；若服务器 Health 变了但 UI 不变，查属性复制与 OnRep；若只小怪打不到，查碰撞对象类型、胶囊高度和投射物轨迹。不要一开始就把伤害乘二“试试看”。
